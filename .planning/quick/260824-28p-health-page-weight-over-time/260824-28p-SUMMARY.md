## The thing that had to be solved first

`Cat.weight` is a **single scalar**. A time series needs many dated readings, so
there was nothing to plot. `types/healthRecord.ts` already modelled exactly the
missing piece and was **completely unused** — no storage, no slice, no
references — with a doc comment that anticipates this chart. The work was to
make that type real, not to design something new.

## Decisions

1. **`Cat.weight` stays the profile's current weight; HealthRecord is the
   history.** Nothing existing breaks. Reversible later into a derived read.
2. **The existing profile weight is not back-filled as a chart point.** We know
   the number, not the date it was taken. Putting it on a timeline would invent
   a measurement date. The empty state explains this rather than hiding it.
3. **No charting dependency** — hand-drawn SVG. Deps need team discussion.
4. **X is proportional to elapsed time, not index.** Even spacing would imply a
   weighing cadence the owner never kept.
5. **Trend is first-to-last, not a fitted slope** — a regression over five
   readings implies precision the data does not have. "Steady" is a 0.1lb band
   because scales disagree with themselves by ounces.
6. **No breed-typical weight baseline.** `lib/breeds.ts` has energy,
   friendliness, grooming, vocality — no weight. A healthy-range band would mean
   inventing veterinary data.

Three more commits after the original scope, driven by testing:

**Validation** (`lib/healthValidation.ts`, 16 tests) catches mistakes that were
previously saved silently: a decimal-point typo (112 for 11.2), pounds typed
into a kg form, a future date — the input's `max` is only a browser hint — a
date before the cat was born, and a duplicate date. `today` is injected so the
future-date rule is testable on any day.

**Editing** arrived because Heidi misclicked a date while testing and had no way
to fix it short of clearing localStorage. Click any chart point or reading row.
A record is excluded from its own clash check, or re-saving an unchanged reading
would be rejected for colliding with itself.

**Comparison chart** shares one pair of axes across cats — scaling per line
would make a comparison chart lie about the thing it compares. Hovering the key
fades the others rather than hiding them.

Also fixed: `crypto.randomUUID` is undefined outside a secure context, so saving
threw when the dev server was reached over http from a phone — exactly how this
gets tested.

165 tests passing.

## The data ceiling this hit

`ScheduleEvent` has **no completion or actual field**. The app records the
*plan* — "feed 0.5 cup daily at 8am" — never whether it happened or how much was
really eaten. So:

- **"Should eat"** — available now, from `feedingAmounts` per cat.
- **"Actually ate"** — no data exists anywhere.
- **"Play time per day"** — only *planned* minutes, from `durationMinutes`.

Every "actual" question needs one architectural addition: a record saying a
planned thing happened, and to what extent. That single addition unlocks
planned-vs-actual for feeding, play, medication adherence and grooming at once.

Owner-measured metrics (water intake, temperature, litter output) are a
different and much cheaper path — `HealthRecord` takes new optional fields by
design.

**This should now be a roadmap phase.** Two quick tasks have landed substantial
feature work while Phase 1 sits unplanned.
